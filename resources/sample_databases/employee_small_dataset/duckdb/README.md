# Employee Sample Database for DuckDB

A DuckDB version of the `mysql/dataset_small` employee database. This
folder is self-contained — it does **not** read from `../mysql/` at
any point. All data lives under `data/` as CSV files.

## Contents

```
duckdb/
├── create_duckdb.sh   # builds employee.duckdb from sql/ + data/
├── sql/
│   ├── 01_schema.sql                     # CREATE TABLE statements
│   ├── 02_load_data.sql                  # COPY ... FROM data/*.csv
│   ├── 03_extra_unassigned_employees.sql # 3 employees, no department
│   ├── 04_extra_empty_departments.sql    # 3 departments, no employees
│   ├── 05_views.sql                      # dept_emp_latest_date, current_dept_emp

├── employee_notebook.py  # Marimo notebook: 14 practice queries + plots
└── employee.duckdb       # generated by create_duckdb.sh
```


## Tables

| Table | Rows (base data) | What it holds |
|-------|------------------:|----------------|
| `department` | 9 | department code + name |
| `employee` | 1,000 | name, birth date, gender, hire date |
| `dept_emp` | 1,103 | employee ↔ department history |
| `dept_manager` | 16 | employee ↔ department manager history |
| `title` | 1,470 | job titles held over time |
| `salary` | 9,488 | salary history |

`create_duckdb.sh` adds, on top of the base data:

- **3 employees with no department** (`emp_no` 20001–20003)
- **3 departments with no employees** (`dept_no` d010–d012)

These give students real rows to find with `LEFT JOIN ... IS NULL`
queries — in the original dataset every employee has a department and
every department has employees, so those queries would otherwise
return nothing.

## Macros, Views, and Table Macros (`sql/06_object.sql`)

A DuckDB port of `mysql/dataset_small/object.sql`. MySQL stored
FUNCTIONs/PROCEDUREs become DuckDB MACROs — scalar macros for
single-value lookups, and table macros (`AS TABLE ...`) for routines
that return a result set:

| Name | Kind | What it does |
|------|------|----------------|
| `emp_dept_id(emp_no)` | scalar macro | current department code of an employee |
| `emp_dept_name(emp_no)` | scalar macro | current department name of an employee |
| `emp_name(emp_no)` | scalar macro | `"first_name last_name"` of an employee |
| `current_manager(dept_no)` | scalar macro | name of a department's most recent manager |
| `v_full_employee` | view | every employee + their current department |
| `v_full_department` | view | every department + its current manager |
| `show_department()` | table macro | department, manager, employee count — call as `SELECT * FROM show_department();` |
| `employee_help()` | table macro | usage help — call as `SELECT * FROM employee_help();` |

## Use of DuckDB Macros

A **macro** is a saved SQL formula that you can call by name, the
same way you call a function in Python. Instead of retyping a query
every time, you save it once and reuse it.

DuckDB has two kinds of macros:

- **Scalar macro** — returns a single value. Use it anywhere you
  would use a column, like inside `SELECT` or `WHERE`.
- **Table macro** — returns many rows and columns, like a saved
  `SELECT` query. Call it inside `FROM`, with parentheses:
  `FROM my_table_macro()`.

All the macros in this database are created by
[`sql/06_object.sql`](sql/06_object.sql). Run `01_schema.sql` and
`05_views.sql` first — the macros depend on the tables and views
those files create.

### Scalar macro examples

```sql
-- emp_name(emp_no) returns "first_name last_name"
SELECT emp_name(10001) AS name;
-- Georgi Facello

-- emp_dept_id(emp_no) returns the employee's current department code
SELECT emp_dept_id(10001) AS dept_id;
-- d005

-- emp_dept_name(emp_no) returns the current department name
SELECT emp_dept_name(10001) AS dept_name;
-- Development

-- current_manager(dept_no) returns the department's current manager
SELECT current_manager('d001') AS manager;
-- Alejandro Brender

-- a scalar macro can be called once per row, just like a column
SELECT emp_no, emp_name(emp_no), emp_dept_name(emp_no)
FROM employee
WHERE emp_no IN (10001, 10002, 10003)
ORDER BY emp_no;
```

### Writing your own macro

```sql
-- scalar macro: body is a single expression
CREATE OR REPLACE MACRO full_title(t, dept) AS (
    t || ' — ' || dept
);
SELECT full_title('Engineer', 'Development');
-- Engineer — Development

-- table macro: body is a query, marked with "AS TABLE"
CREATE OR REPLACE MACRO employees_in_dept(dept_id) AS TABLE
    SELECT emp_no, emp_name(emp_no) AS name
    FROM current_dept_emp
    WHERE dept_no = dept_id;

SELECT * FROM employees_in_dept('d005') LIMIT 5;
```

> **Good to know:** if a macro selects `FROM` a table that shares a
> name with a table in the query calling it (for example, a macro
> reading `FROM employee` used inside `SELECT ... FROM employee`),
> always give that table an alias inside the macro, e.g.
> `FROM employee AS e`. DuckDB inlines the macro's SQL into the
> caller's query, and without an alias it can confuse the two scans
> and raise `More than one row returned by a subquery used as an
> expression` for what should be a single-row lookup. Every macro in
> `06_object.sql` uses an alias for this reason.

## Usage

```bash
cd duckdb

# builds employee.duckdb
./create_duckdb.sh 

# open the practice-queries notebook
marimo edit employee_notebook.py
```

* `create_duckdb.sh` requires the 
[DuckDB CLI](https://duckdb.org/docs/installation/)
on your `PATH`. 

* `employee_notebook.py ` requires `marimo`, `duckdb`, `pandas`,
and `matplotlib` (see `course_information/REQUIRED_SOFTWARE.md`).
