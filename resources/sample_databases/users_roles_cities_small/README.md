# Users / Roles / Cities Sample Database

A tiny, three-table DuckDB database used to practice `SELECT`,
`JOIN`, `GROUP BY`, and `LEFT JOIN ... IS NULL` without the noise of
a big dataset. Everything lives in this one folder — no external
downloads, no server to install.

## The Story

Imagine a small internal tool that a company uses to track its
people. Every person who logs in is a **user**. Every user is
assigned exactly one **role** (what they're allowed to do) and lives
in one **city** (for reporting and support routing).

The team that built this system defined all the roles and all the
cities they *might* ever need, up front — five roles, six cities —
long before they had employees to fill every one of them. Today,
17 users have signed up. Naturally, not every role and not every
city has been claimed yet:

- **`tester`** and **`QA`** are defined roles, but no one has been
  assigned either one — those job functions haven't been staffed.
- **`Cupertino`** and **`Detroit`** are defined cities, but nobody
  lives there yet — the company hasn't hired in those offices.
- Three names — **`Max`**, **`Barb`**, and **`Jane`** — each belong
  to *two different people* with different `id`s, a reminder that
  `name` is not a reliable way to identify a user.

This is exactly the kind of "not everything is used yet" data you
run into in real systems, and it's what makes `LEFT JOIN ... IS
NULL` and `GROUP BY ... HAVING` genuinely useful instead of just
textbook exercises.

## Tables

| Table | Rows | Columns | What it holds |
|-------|-----:|---------|----------------|
| `roles`  | 5  | `id`, `role` | admin, user, superuser, tester, QA |
| `cities` | 6  | `id`, `city` | New York, Philadelphia, San Francisco, Sunnyvale, Cupertino, Detroit |
| `users`  | 17 | `id`, `name`, `role_id` (FK → `roles.id`), `city_id` (FK → `cities.id`) | one row per person |

```
roles (id, role)          cities (id, city)
       ▲                          ▲
       │ role_id                  │ city_id
       └──────────── users ───────┘
              (id, name, role_id, city_id)
```

## Data Gaps (by design)

| Question | Answer | Found by |
|----------|--------|----------|
| Which roles are never used? | `tester`, `QA` | `LEFT JOIN roles → users, WHERE u.id IS NULL` (notebook query **I5**) |
| Which cities have no users? | `Cupertino`, `Detroit` | `LEFT JOIN cities → users, WHERE u.id IS NULL` (notebook query **I6**) |
| Which names repeat? | `Max`, `Barb`, `Jane` | `GROUP BY name HAVING COUNT(*) > 1` (notebook query **I9**) |

## Usage

```bash
cd users_roles_cities

# builds users_roles_cities.duckdb
./create_duckdb.sh

# open the practice-queries notebook
marimo edit notebook.py
```

- `create_duckdb.sh` requires the
  [DuckDB CLI](https://duckdb.org/docs/installation/) on your `PATH`.
- `notebook.py` requires `marimo`, `duckdb`, `pandas`, and
  `matplotlib` (see `software_installation/README.md`).

## The 20 Practice Queries

`notebook.py` has 20 SQL cells, grouped by difficulty:

| Level | Count | Focus |
|-------|------:|-------|
| Simple (S1–S10) | 10 | `SELECT`, `WHERE` + `LIKE`, `WHERE` + `IN`, `ORDER BY`, `LIMIT`, `DISTINCT`, `COUNT(*)` |
| Intermediate (I1–I10) | 10 | `JOIN`, `GROUP BY`, `LEFT JOIN` + `IS NULL`, `HAVING`, multi-column `GROUP BY` |

Five of the intermediate queries also produce a chart, using
plotting functions imported from `plot_helpers.py` (kept outside the
notebook, on purpose, so the notebook cells stay focused on SQL):

| Query | Chart | What it shows |
|-------|-------|----------------|
| I3 | bar | Users per role |
| I4 | bar | Users per city |
| I8 | pie | Role distribution (%) |
| I9 | horizontal bar | Names shared by more than one user |
| I10 | horizontal bar | Top 5 role + city combinations |
