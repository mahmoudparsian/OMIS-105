# Authors / Books / Orders — Join Practice Database

A small, three-table DuckDB database for learning `INNER JOIN`,
`LEFT JOIN`, and `RIGHT JOIN`, with a little aggregation along the
way. Everything lives in this one folder — no external downloads,
no server to install.

## The Story

Imagine a small online bookstore. It works with a few **authors**.
Each author may write some **books**, and customers place
**orders** to buy them. Each order is one copy of one book.

The store signed 6 authors and lists 20 books. During 2025,
customers placed 80 orders. Not everything connects:

- **Priya Sharma** and **Omar Haddad** signed with the store, but
  have not published a book yet.
- **4 books were never ordered:** B06, B12, B17, B20. Each one comes
  from a different author — every author who published has exactly
  one book that never sold.
- Authors do not write the same number of books: 8, 6, 4, 2, 0, 0.

This "not everything matches" data is common in real systems. It is
what makes `INNER JOIN`, `LEFT JOIN`, and `RIGHT JOIN` give
different answers, and what makes `LEFT JOIN ... IS NULL` useful.

## Tables

| Table | Rows | Columns | What it holds |
|-------|-----:|---------|----------------|
| `authors` | 6  | `author_id`, `name`, `email`, `age`, `country` | one row per author; `email` is unique |
| `books`   | 20 | `book_id`, `author_id`, `title`, `category`, `publication_year` | one row per book; `book_id` is text (`B01`–`B20`); 3 categories: `SPORT`, `BUSINESS`, `COMPUTERS` |
| `orders`  | 80 | `order_id`, `book_id`, `sale_price`, `order_date` | one row per copy sold; prices $20–$49 (whole dollars); dates in 2025 |

```
authors (author_id, name, email, age, country)
   ▲
   │ books.author_id → authors.author_id
books (book_id, author_id, title, category, publication_year)
   ▲
   │ orders.book_id → books.book_id
orders (order_id, book_id, sale_price, order_date)
```

The chain is **authors → books → orders**. One author writes many
books. One book can be sold many times.

Both links are enforced by a `FOREIGN KEY` in `db_schema.sql`.
Every `books.author_id` must exist in `authors`, and every
`orders.book_id` must exist in `books` — DuckDB rejects anything
else. A `FOREIGN KEY` only checks the child side, so an author with
no books, or a book with no orders, is still allowed. Those are the
gaps below.

## Data Gaps (by design)

| Question | Answer | Found by |
|----------|--------|----------|
| Which authors have no books? | Priya Sharma (5), Omar Haddad (6) | `authors LEFT JOIN books ... WHERE b.book_id IS NULL` (notebook **M1**) |
| Which books were never ordered? | B06, B12, B17, B20 | `books LEFT JOIN orders ... WHERE o.order_id IS NULL` (notebook **M2**, **M3**) |
| Who wrote the unsold books? | one each: Maria Lopez, James Carter, Aiko Tanaka, Lars Nilsson | 3-table join (notebook **M4**) |

## Usage

**Step 1 — build the database file** (needed for both the notebook
and the CLI):

```bash
cd joins_with_authors_books_orders
./create_duckdb_database.sh         # creates authors_books_orders.duckdb
```

Run it again any time — it deletes and rebuilds the file. It needs
the [DuckDB CLI](https://duckdb.org/docs/installation/) on your
`PATH`.

**Step 2a — Notebook:**

```bash
marimo edit notebook.py
```

The notebook opens the database **read-only**: you can run any
`SELECT`, but nothing can change the data. If the `.duckdb` file is
missing, the notebook stops and tells you to run Step 1.

**Step 2b — DuckDB CLI or qStudio:**

```bash
duckdb -readonly authors_books_orders.duckdb    # then paste any query
```

`notebook.py` requires `marimo`, `duckdb`, `polars` (or `pandas`), and
`matplotlib` (see the
[software installation guide](../../../software_installation/README.md)).

## The 26 Notebook Queries

| Part | Queries | Focus |
|------|---------|-------|
| 1. Meet the data | V1–V3 | One `SELECT` per table |
| 2. A little aggregation | A1–A3 | `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`, `GROUP BY`, `LIMIT` |
| 3. `INNER JOIN` ⋈ | J1–J5 | 2- and 3-table joins; join + `GROUP BY` |
| 4. `LEFT JOIN` ⟕ | J6–J9 | NULL-filled rows; `COUNT(*)` vs. `COUNT(column)`; `COALESCE`; filter in `ON` vs. `WHERE` |
| 5. `RIGHT JOIN` ⟖ | J10–J12 | `A LEFT JOIN B` = `B RIGHT JOIN A`; `COUNT(DISTINCT ...)` |
| 6. Finding what is missing | M1–M4 | `LEFT`/`RIGHT JOIN` + `IS NULL` (anti-join) |

The notebook ends with a row-count comparison of every join type, a
cheat sheet, and five "Try It Yourself" exercises.

### The 5 charts

Five queries are followed by a chart. The plotting code lives in

| Query | Chart | What it shows |

### Row counts to watch

| Join | Rows |
|------|-----:|
| `authors INNER JOIN books` | 20 |
| `authors LEFT JOIN books` | 22 |
| `books RIGHT JOIN authors` | 22 |
| `books INNER JOIN orders` | 80 |
| `books LEFT JOIN orders` | 84 |
| `orders RIGHT JOIN books` | 84 |

The extra rows in each outer join are exactly the gaps above: 2
authors with no books, 4 books with no orders.
