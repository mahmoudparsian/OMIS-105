# Students / Courses / Grades — Join Practice Database

A three-table DuckDB database for learning `INNER JOIN`,
`LEFT JOIN`, and `RIGHT JOIN`, with some aggregation along the way.
Everything lives in this one folder — no external downloads, no
server to install.

## The Story

A small university tracks the grades of its students. Each student
may take any number of courses. Each time a student finishes a
course, one row is added to `grades`.

The university has 500 students and offers 50 courses. Between 2021
and 2025 it recorded 8,000 grades. Not everything connects:

- **5 students have never taken a course:** student_id 37, 142,
  256, 391, 478.
- **3 courses have never been taken:** ENGR204 (Robotics),
  MATH204 (Optimization Theory), FIN204 (Fintech and Digital
  Payments).

This "not everything matches" data is common in real systems. It is
what makes `INNER JOIN`, `LEFT JOIN`, and `RIGHT JOIN` give
different answers, and what makes `LEFT JOIN ... IS NULL` useful.

## Tables

| Table | Rows | Columns | What it holds |
|-------|-----:|---------|----------------|
| `students` | 500   | `student_id`, `first_name`, `last_name`, `major`, `gender`, `country` | one row per student; most are from the USA, India, and China |
| `courses`  | 50    | `course_id`, `course_name`, `course_level`, `num_of_credits` | 10 courses per department (BUS, ENGR, MATH, CSCI, FIN); `1xx` = undergraduate, `2xx` = graduate |
| `grades`   | 8,000 | `grade_id`, `student_id`, `course_id`, `year`, `grade` | one row per student per course; years 2021–2025; grades `A`–`F` |

```
students (student_id, first_name, last_name, major, gender, country)
   ▲
   │ grades.student_id → students.student_id
grades (grade_id, student_id, course_id, year, grade)
   │
   │ grades.course_id → courses.course_id
   ▼
courses (course_id, course_name, course_level, num_of_credits)
```

`grades` sits in the middle: it links students to courses. Both
links are enforced by a `FOREIGN KEY` in `db_schema.sql`. A
`FOREIGN KEY` only checks the child side, so a student with no
grades, or a course with no grades, is still allowed. Those are the
gaps above.

`major`, `gender`, `country`, `course_level`, and `grade` are `ENUM`
types: they only accept values from a fixed list. For `grade`, the
list order is `A, B, C, D, F`, so `ORDER BY grade` sorts best to
worst.

## Usage

**Step 1 — build the database file:**

```bash
cd joins_with_students_and_courses
./create_duckdb_database.sh         # creates students_courses_grades.duckdb
```

Run it again any time — it deletes and rebuilds the file. It needs
the [DuckDB CLI](https://duckdb.org/docs/installation/) on your
`PATH`.

**Optional — regenerate the data.** `db_records.sql` is written by
`generate_db_records.py`. The random seed is fixed, so the script
always writes the same rows. To change the data, edit the settings
at the top of the script (seed, gaps, grade mix), then run:

```bash
python3 generate_db_records.py      # rewrites db_records.sql
./create_duckdb_database.sh         # rebuilds the database
```

If you change which students or courses are left out, update the
numbers in this README and in `notebook.py` too.

**Step 2a — Notebook:**

```bash
marimo edit notebook.py
```

The notebook opens the database **read-only**: you can run any
`SELECT`, but nothing can change the data. If the `.duckdb` file is
missing, the notebook stops and tells you to run Step 1.

**Step 2b — DuckDB CLI or qStudio:**

```bash
duckdb -readonly students_courses_grades.duckdb    # then paste any query
```

`notebook.py` requires `marimo`, `duckdb`, `polars` (or `pandas`), and
`matplotlib` (see the
[software installation guide](../../../software_installation/README.md)).

## The 16 Notebook Queries

| Part | Queries | Focus |
|------|---------|-------|
| 1. Meet the data | V1–V3 | One `SELECT` per table |
| 2. Aggregation | A1–A3 | `COUNT`, `COUNT(DISTINCT ...)`, `GROUP BY` |
| 3. `INNER JOIN` ⋈ | J1–J4 | 2- and 3-table joins; join + `GROUP BY`; GPA with `CASE` |
| 4. `LEFT JOIN` ⟕ | J5–J7 | `COUNT(*)` vs. `COUNT(column)`; anti-join with `IS NULL` |
| 5. `RIGHT JOIN` ⟖ | J8–J10 | `A LEFT JOIN B` = `B RIGHT JOIN A`; `NULLS FIRST`; why `CASE` has no `ELSE` |

The notebook ends with a row-count comparison of every join type, a
cheat sheet, and five "Try It Yourself" exercises.

### The 6 charts

| Query | Chart | What it shows |
|-------|-------|----------------|
| A1  | horizontal bar | Students per country |
| A2  | bar | Count and share of each letter grade, A to F |
| A3  | line | Grades recorded per year, 2021–2025 |
| J4  | horizontal bar | Average GPA by department, on a 0–4 scale |
| J7  | bar | Students per graduate course — the 3 courses nobody took show as dashed "none" bars, kept by the `LEFT JOIN` |
| J9  | stacked bar | Courses offered per department: taken vs. never taken |

### Row counts to watch

| Join | Rows |
|------|-----:|
| `students INNER JOIN grades` | 8,000 |
| `students LEFT JOIN grades`  | 8,005 |
| `grades RIGHT JOIN students` | 8,005 |
| `courses INNER JOIN grades`  | 8,000 |
| `courses LEFT JOIN grades`   | 8,003 |
| `grades RIGHT JOIN courses`  | 8,003 |

The extra rows in each outer join are exactly the gaps above: 5
students with no grades, 3 courses with no grades.

## SQL Interview Practice

Data analyst interviews almost always include a live SQL test.
`interview_practice.py` has 12 interview-style questions on this
database, written the way a manager would ask them. Set a timer for
60 minutes.

```bash
marimo edit interview_practice.py           # the questions
marimo edit interview_practice_answers.py   # the answers — open after you try
```

Under each question, a box checks your **row count and column
names**: green means the shape of your result is right. The
questions get harder:

| Level | Questions | Skills |
|-------|-----------|--------|
| Warm-up | Q1–Q4 | `GROUP BY`, `HAVING`, anti-join, join + `LIMIT`, ties |
| Core | Q5–Q9 | filter in `ON` vs. `WHERE`, conditional counts, `COUNT(DISTINCT)`, 3-table joins |
| Hard | Q10–Q12 | weighted averages, a correct answer with 0 rows, an unclear question |

The answers notebook explains what each question is really testing,
and runs the most common wrong answer next to the right one, so you
can see how the results differ.
