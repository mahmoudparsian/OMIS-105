# Data-Quality Round — Students / Courses / Grades

**Optional, advanced.** Do the joins notebook in the parent folder
first.

Real data is messy. Before any report, analysts check it. This
folder builds a **second, messy copy** of the students / courses /
grades database: three `raw_` tables, as if exported from an old
system with no rules, so bad data got in. Your job is to find every
problem and count the rows it affects.

## File Structure

```
data_quality/
├── README.md                              # this file
├── create_messy_database.sh               # builds students_courses_grades_messy.duckdb
├── db_messy.sql                           # raw_ copies with planted problems (SPOILER)
├── data_quality.py                        # the 14 checks, with automatic checks
├── data_quality_answers.py                # solutions, tempting wrong queries, which rules stop each problem
└── students_courses_grades_messy.duckdb   # generated by create_messy_database.sh (not committed)
```

The build script reuses the clean `../db_schema.sql` and
`../db_records.sql` from the parent folder. The clean database is
not touched.

## Usage

```bash
cd joins_with_students_and_courses/data_quality
./create_messy_database.sh            # creates students_courses_grades_messy.duckdb
marimo edit data_quality.py           # the 14 checks
marimo edit data_quality_answers.py   # the answers — open after you try
```

The build script needs the
[DuckDB CLI](https://duckdb.org/docs/installation/) on your `PATH`.
Don't open `db_messy.sql` first: it lists every planted problem.

## The Tables

| Table | Rows | Columns |
|-------|-----:|---------|
| `raw_students` | 504   | `student_id`, `first_name`, `last_name`, `major`, `gender`, `country` |
| `raw_courses`  | 50    | `course_id`, `course_name`, `course_level`, `num_of_credits` |
| `raw_grades`   | 8,013 | `grade_id`, `student_id`, `course_id`, `year`, `grade` |

Every text column is plain `VARCHAR`. There are no keys and no
`NOT NULL` rules.

## The 14 Checks

| Part | Checks | What you look for |
|------|--------|-------------------|
| A. Profile | DQ1 | rows vs. unique ids in each table |
| B. Students | DQ2–DQ7 | duplicate ids, exact vs. conflicting copies, country spellings, missing names (`NULL` and `''`), invalid codes |
| C. Courses | DQ8 | invalid levels, 0 credits |
| D. Grades | DQ9–DQ14 | orphan rows (anti-join), impossible years, invalid or `NULL` grades, the same row loaded twice, reused ids |

The answers notebook ends with a one-query **data-quality report**.
It then tests `../db_schema.sql` directly: it tries to insert one bad
row of each kind into an empty copy of the clean schema. 10 of the
14 are rejected, and 4 get through, because no `CHECK` or `UNIQUE`
rule covers them.
